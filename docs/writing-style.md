# 写作规范

适用于 README、`docs/`、`CHANGELOG.md`、界面文案、PR 与 issue。目标是把话说清楚，不推销、不抒情、不堆术语。

## 语气

- 写事实和做法：现在是什么、为什么这样、怎么操作。不写愿景、意义和「我们相信」。
- 一句话只讲一件事。超过 40 字就拆开，或者改成列表。
- 主语尽量具体：页面、脚本、索引、manifest，少用「我们」和「系统」。
- 不替读者下结论。说明限制和取舍，让读者自己判断。
- 不确定的数字、效果、性能，标注日期或不说。

## 用词

- 不堆形容词：直观、强大、轻松、深度、极致、无缝、一站式、一目了然、完美。
- 不用产品/设计黑话：赋能、闭环、抓手、心智、锚点、叙事、降噪、颗粒度、对齐（当动词）、保驾护航。
- 不写口号式对偶：「不是 A，而是 B」「不只 A，更是 B」「从 A 到 B」。
- 不写填充句：「值得注意的是」「不难看出」「众所周知」。
- 不把英文习语直译成中文，例如把 card soup 写成「卡片汤」。直接说「卡片泛滥」。
- 代码、命令、字段名用反引号；中英文之间加空格；数字用半角。

## 句子与标点

- 破折号（——）少用。中文里的停顿用「：」或逗号，一段最多一次。
- 中文引号用「」，并列项用顿号，句末不加感叹号。
- 标题用名词或动词短语，不用问句。「这场发生了什么」只适合作为设计文档里的用户问题。
- 列表项保持同一语法结构，一条一个意思；能写成三行短句的，不要写成一段长句。
- 链接文字写清指向（`docs/engineering/deployment.md`），不写「点击这里」「详见上文」。

## 界面文案

- 按钮和标签用动词或名词短语：`复制链接`、`清除筛选`、`更新日历`。
- 空状态说三件事：这里是什么、为什么空、下一步怎么做。不写「暂无数据」了事，也不写道歉和抒情句。
- 错误提示给可执行的下一步（重试、检查配置、看日志），不要只抛出异常名。
- 不解释显而易见的交互（「点击这里可以打开」），不为同一个数字写两条说明。
- 文案里出现数字时带单位：`1,891 场`、`6,910,832 条弹幕`、`29,010 笔 SC`。

## 术语

| 用 | 不用 | 备注 |
| --- | --- | --- |
| 同接 | 在线人数、人气 | 沿用 VSTATS 的说法 |
| 弹幕 | 聊天、评论 | `评论` 专指视频评论区 |
| SC | 打赏、付费消息 | 首次出现可写「SC（スーパーチャット）」 |
| 场次 / 单场 | 直播场、视频 | `场次` 是列表，`单场` 是详情 |
| 口径 | 算法、统计方式 | 首次出现可解释 |
| 会员限定 | 会限 | 正文第一次写全称 |
| JST / 日本时间 | 东京时间 | 时间一律 JST |
| 逐字稿 | 文字稿、字幕 | 字幕指 YouTube CC，不混用 |

## 工程与迁移术语

迁移到 Astro 后，下面这些词会频繁出现；先确定用词，再写进文档和界面。

| 用 | 不用 | 说明 |
| --- | --- | --- |
| 页面 | 界面、视图（混用） | 路由渲染出的完整页面 |
| 岛屿 | 交互组件、客户端组件 | 带 `client:*` 指令的 React 组件 |
| 水合 | 激活、挂载（混用） | 浏览器下载并执行岛屿 JavaScript 的过程 |
| 构建时 | 编译时（混用） | `astro build` 执行阶段 |
| 按需渲染 | SSR（单独使用） | `prerender = false`，请求到达时执行 |
| 预渲染 | 静态化（混用） | `prerender = true`，构建时输出 HTML |
| 设计 Token | 颜色变量、主题色 | CSS 变量与 Tailwind 映射 |
| 门禁 | 检查、校验（混用） | 固定组合的验证命令 |
| 验收标准 | 测试点、检查项（混用） | 可观察、可失败的行为断言 |
| 数据获取 | 请求、拉取（混用） | 构建期读取或请求期查询 |
| 回退 | 兜底、降级（混用） | 主数据源不可用时改用本地内容或内置数据 |

## AI 协作

- 不复述显而易见的内容，不写「总结如下」这类套话。
- 验证结果如实写：跑了什么命令、通过还是失败、哪些没跑以及原因。
- 不确定的写「未验证」，不猜数字、时间和效果。
- 不用「已完成」掩盖未验证的部分。
- 迁移类文档必须区分「当前实现」与「目标形态」；未实现的能力标 `📋`。

## 反例

| 反例 | 改写 |
| --- | --- |
| 把五人团的直播读成一份可回看的观赛笔记。 | 记录五位成员已结束的直播，提供读数、回看和归属三类内容。 |
| 不是数据不够，是缺少图像层与叙事层。 | 数据已经够用，缺的是画面。 |
| 密度不是问题，均匀的密度才是问题。 | 信息可以密，但不要所有东西一样密。 |
| 这轮重构不是把信息做少，而是把视觉重量重新分配。 | 这轮重构不删信息，只重新分配视觉重量。 |
| 表格仍然是产品资产，而不是被卡片列表替代的对象。 | 表格仍是主要浏览方式。 |
| 这是卡片汤的根源。 | 这是之前卡片泛滥的原因。 |
| 封面就会重新按 JST 自然月排上来。 | 换个条件，或者清除筛选。 |
| 首页降噪与溢出修复。 | 首页排版与溢出修复。 |
| Quiet shell, dense data（壳静，数据密）。 | 壳静，数据密。（中文文档里不重复英文口号） |

## 事实与引用

- 写进文档的路径、命令、路由、字段名都要能对上当前代码；不确定就先跑一遍。
- 删文件、改路由、改脚本参数时，全局搜一遍旧写法再提交：`rg "旧路径|旧命令" README.md docs`。
- 不把计划当现状：没做的放 [backlog.md](planning/backlog.md)，文档里只写已经成立的事实。
- 截图、数字、性能指标标日期；页面改版后替换或删掉过期图片，不留坏链。

## 提交前检查

```bash
# 命中就人工看一遍，不是全部都要改；没装 ripgrep 就用编辑器的全局搜索
rg -n "直观|强大|轻松|深度|极致|无缝|一站式|一目了然|赋能|闭环|抓手|心智|锚点|叙事|降噪|颗粒度|不是.{0,12}而是|不只.{0,12}更|值得注意的是|众所周知" README.md docs src
```

- 新写的段落能否用一句话概括？不能就拆。
- 每个形容词能否删掉而不损失信息？能就删。
- 界面文案是否说清了「是什么、为什么、下一步」？
- 数字是否有单位、日期和来源？
