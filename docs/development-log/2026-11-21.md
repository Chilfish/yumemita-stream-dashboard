## 官方账号场次：POC

### 背景

成员个人频道之外，官方账号也会开多人直播。两个例子性质完全不同：

- `@BDP_yumemita`（团体号）：71 场，整条频道都是本团内容。
- `@bang_dream_official`（企划母频道）：453 场，本团只出演其中一部分，出演信息只在简介的「出演者」区块。

成员频道里的联动场不能覆盖这类内容：那里的主场仍是某位成员，指标天然属于他；官方场次的主场是团体或企划方。

### 结论

1. 官方场次用独立 dataset 承载，`datasets` 加 `kind`（`member` / `official`）。
2. 官方场次的 `participants` 表示**在场的成员**，不并入成员个人场次；成员维度查询加「owner 是成员」的前提。
3. 每日自动更新只覆盖 `sync` 为 `channel` / `filtered` 的账号；第三方账号用 `data official` 手动添加，参与者作为参数传入。
4. 日历与全组相册包含官方场次；成员页、成员榜、出勤、联动矩阵、对比、SEO 人数都不含。

方案与验收标准见 [official-channels.md](../planning/official-channels.md)。

### 实现（POC 范围）

| 层 | 改动 |

### POC 中暴露并修掉的问题

1. 官方 dataset 缺 `dataset_insights` 行时成员页模板抛 `useDatasetView must be used within DatasetViewContext.Provider`。正式实现要让 ingest 为官方 dataset 生成 insights。
2. `llms.txt` 调用方没传 `kind`，官方账号被列进成员段。
3. SEO 与页头人数把官方账号算进去，统一走 `countMembers()`。
4. 相册筛选按 id 排序，官方账号夹在成员之间；改为 `kind` 优先、再按 id。
5. 日历按成员筛选会因官方场次的 `participants` 带出整场；改为 `memberKind === 'official'` 时跳过参与者匹配。
6. `data fetch` 强制要求 `channelId`，`other` 无法使用；改为只在需要拉频道列表时要求。

## 正式实施：补齐 `yumemita`

### 改动

`data-sources.json` 增加 `participants`，取值 `all` / `cast` / `none`，决定官方场次的成员从哪来：

- `yumemita` → `all`：整频道默认全员在场。
- `bangdream` → `cast`：只取简介「出演者 / キャスト」区块命中的成员。
- `other` → `none`：不推断，只认 `content/collaborations.json` 的登记。

`resolveParticipants` 增加官方分支：登记 > 规则；官方场次**不再回落标题推断**（传 `official: null` 时直接返回空）。`castFromDescription` 只截取出演者区块，避免扫到简介模板里的全员名单。新增 12 条单测。

```bash
bun run ymmt data fetch --dataset yumemita --concurrency 4 --build-every 5 --no-publish
```

### 验证

- 本地库：71 场全部 5 位参与者、insights 自动生成、成员场次数等于「owner + 成员频道联动」，成员与官方无重复 videoId。
- 页面：`/yumemita`、`/yumemita/streams`、`/yumemita/stream/u7f5p223ByA` 均 200；`/nonoka/stream/u7f5p223ByA` 404；成员页不含官方场次；全组相册与 sitemap 收录官方场次；组首页仍为「5 位成员」。
- `bunx tsc --noEmit` 无 src 错误；`vitest run` 569 passed；`bun run build` 通过。

### 遇到的两个坑

1. **线上库缺 `kind` 列。** 本地迁移完成后直接 `db ingest` 线上会因缺列失败；先 `LOCAL=0 bun run ymmt db migrate` 再 ingest。
2. **本地封面空白。** 首次发布用 `LOCAL=0` 只写了线上 R2，而本地页面读 SILO 桶。需要在 `LOCAL=1` 下再跑一次 `publish data --assets-only`；两套桶互不影响，线上和本地各发布一次才都正常。

- `bangdream` 的 `filtered` 抓取（标题粗筛 + 简介 cast 的候选过滤）还没接进 `data fetch`。
- `other` 还没有真实场次；`data official` 只在 dry-run 与单测里验证过。

## 高频词：笑声词形归一

### 背景

单场「高频词」里 `www` / `ww` / `wwwww` / `wwwwww` 各占一条，把榜位吃满；同一种「笑」被拆成了多个词。

### 改动

| 层 | 改动 |
| --- | --- |
| 纯函数 | `src/lib/stopwords.ts` 新增 `canonicalWord`：连续半角 / 全角 `w`（不分大小写）统一成 `www` |
| 分词 | `data datapack` 与 `scripts/oneoff/enrich-chat.ts` 的 `countWords` 按归一化词形累加 |
| 入库 | `db ingest` 的 `collectWords` 先合并再卡 `count >= 3`，同一场不会写入多条笑声 |
| 聚合 | `aggregateDataset` / `streamTopWords` 按归一化词形合并；`streams` 按场次去重，同一场里多种写法只算一场 |
| 查询 | `computeDatasetPublicTotals` 的词频汇总用 SQL 归一化表达式合并历史行，不必等全量重写 `stream_words` |
| 校验 | `validate content` 的词数对账用同一口径 |

### 验证

`tests/lib/stopwords.test.ts` 覆盖半角 / 全角 / 大小写；`aggregate.test.ts` 覆盖 v1 / v2 合并与跨场 `streams` 去重。`bun run test` 575 passed，`typecheck` / `typecheck:scripts` 通过。

### 备注

- 只归一「笑」本身（`w` 系列），不把 `草` 并进来；`w` 与 `草` 仍是两条语义 / 写法不同的记录。
- 历史 `stream_words` 行没有重写，线上单场页与全期汇总都由读取侧归一；下次 `publish sync --force` 或重跑 ingest 时才会落成规范词形。
