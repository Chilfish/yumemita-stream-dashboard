## 脚本层数据库重复读写

**做了什么**

- `scripts/daily-update.ts`：成员状态从「每个成员 2 条查询」改成一次 `inArray` 取回全部 `streams` 与 `dataset_insights`，用 `runBatch()` 合并为 1 次 HTTP 往返。
- `scripts/ingest-db.ts`：
  - `syncTranscripts()` 先读该成员的 `transcripts.content_hash`，内容未变直接跳过，不再每次 upsert 全部稿件。
  - insights 过期判断把 `dataset_insights` 与 `count(*)` 合成一条查询，每成员少 1 条 SQL。
- `src/db/queries/dataset-totals.ts`：`computeDatasetPublicTotals()` 改为窄 SQL 聚合。`streams` 只取汇总列；词频 / 作者在 SQL 里 `sum + group by`；评论 / 贴纸按场聚合；`stream_details` 只取 badges / hashtags / emojiKinds 与 `density->'perMinute'`。不再还原 pack，也不再加载 paid_events / comments 的完整明细。
- `src/db/schema.ts` / `drizzle/0005_magical_diamondback.sql`：新增 `streams.paid_share_pct`；`ingest-db` 写入，`buildPack()` 与汇总复用精确值。旧行没有值时按每分钟序列近似。
- `src/db/queries/packs.ts`：删除不再使用的 `getDatasetPackSet()` / `getDatasetPacks()`；`buildPack()` 回填 `paidSharePct`。
- `scripts/lib/schedule-sync.ts`：未来场从逐条 upsert 改为一次多行 upsert；缺时刻时用 `coalesce` 保留旧值。
- `scripts/verify-db.ts`：只取对账需要的 5 列；4 条 group by 放进同一个 `runBatch()`。
- `scripts/publish-transcripts.ts` / `scripts/lib/publish-state.ts`：内容未变时复用上次 `contentUpdatedAt`，避免 CI 每天 checkout 改 mtime 导致全部逐字稿重传；索引 `generatedAt` 改成条目里的最新时间，内容不变时索引也不变。
- 文档：更新 [db-optimization.md](../planning/db-optimization.md) §8，登记 backlog B20。

**为什么**

- 每日任务只新增 1 场时，仍会按成员逐条查状态、全量 upsert 逐字稿、全量重算 insights，并在 `computeDatasetPublicTotals()` 里把同一个 dataset 的 `streams` 读两遍。
- `publish-transcripts` 把文件 mtime 写进对象内容，CI 每次 checkout 都会改 mtime，导致 13 篇正文与索引每天重传。
- 上一轮数据库优化只覆盖请求期读路径，离线脚本不在范围内。

**验证**

- `bun run check`：astro check 0 error、323 tests 通过、oxlint 0 warning。
- 用本地 pack 的全量 `aggregateDataset()` 与新 SQL 汇总逐字段比较：除 `topWords` 的低频词尾差外全部一致；`paidSharePct` 由新列恢复为精确值。
- 本地执行 `bun run db:migrate`（`0005_magical_diamondback.sql`）与 `bun scripts/refresh-public-totals.ts`；arale / miyako / nonoka / ritsu 的 `bun run db:verify` 均为 0 problems。
- 本地 `db:verify --dataset yuno` 曾在该成员 ingest 仍在运行时执行，`442/443` 与 `stream_authors` 差异属于中间状态；等该轮 ingest 完成后重跑再确认。

**未做**
