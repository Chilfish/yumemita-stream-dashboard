## Astro + PostgreSQL + Workers 迁移方案

**做了什么**

- 新增 [archive/astro-ssr-migration.md](../archive/astro-ssr-migration.md)：
  - 结论：Astro 7 + Cloudflare Workers + Neon PostgreSQL + R2；数据页请求期 SSR，稳定页预渲染。
  - 数据模型：`datasets` / `streams` / `stream_details` / `paid_events` / `comments` / `authors` / `stream_authors` / `stream_words` / `dataset_insights` / `transcripts` / `ingest_reports`，预留 `chat_events` 分区表。
  - ingest：本地 pack → 事务 upsert → insights → 报告；ingest 用 `postgres` 直连，Worker 读用 `neon-http`。
  - 页面迁移：React Router 解耦、岛屿策略、URL 状态、SEO / sitemap / 404。
  - Agent 视图：`/{datasetId}/stream/{videoId}.md`，返回 `text/markdown`，含概览、部分指标与逐字稿；不做 `Accept` 协商，不启用 Cloudflare Markdown for Agents。
  - 缓存：Astro 7 route caching + Workers Cache；tag purge；ingest 后调内部 purge 端点。
  - 发布：数据更新不触发前端构建；代码部署与数据发布分离。
  - 阶段 0–5、验收清单、风险与待决。

**为什么**

- 旧 SSG 调研的结论是「不推荐 Astro」，前提是整体 SSG；模板的 `output: 'server'` + DB + R2 形态改变了前提。

- `.md` 路由给 Agent 一个稳定、结构化、包含逐字稿的入口。

## 性能排查：路由切换与单场分段

**问题**

- 侧栏路由切换体感比 SPA 慢；单场 `?view=` 切换也要等。
- `astro preview` 下页面 HTML 里内联了 384 KB CSS，且 cache 是 no-op。

**定位**

- `astro preview` 实际按开发模式跑：CSS 内联、`Astro.cache.enabled === false`、不产生 `Cache-Tag`。生产行为要用 `wrangler dev --config dist/server/wrangler.json` 验证。
- 生产构建首屏 HTML：`/nonoka` 408.8 KB、`/nonoka/streams` 322.3 KB、单场 219.7 KB；缓存头与 tag 正常。
- 单场 tab 之前调用 `navigate()`，每次都走 SSR；改为 `history.replaceState` + 岛屿状态后实测 27 ms。
- 对比页切换选中场次时不会拉新 pack，已补 `/api/packs/:datasetId/:videoId` 与按需加载。
- 路由切换仍受 Neon 跨区 RTT 影响：本机每次 SSR 1.5–2.1 s；hover 预取能提前发出请求，但 `wrangler dev` 不复现 Workers Cache HIT。

**改动**

- `build.inlineStylesheets: 'never'`，字体 / Tailwind CSS 外链并长期缓存。
- 岛屿 props 去掉重复 `manifest`；单场 / 对比的 pack 去掉全量 `authors` / `wordCounts`。
- 成员页 datasets / streams / insights 并行查询；`listStreams` 用 `count(*) over()` 一次取总数。
- 所有数据页显式 `Astro.cache.set`，tag 覆盖 `dataset-<id>` / `stream-<videoId>`；middleware 把 `Cloudflare-CDN-Cache-Control` 同步到 `Cache-Control`，让预取可被浏览器复用。
- 页面岛屿改为 `client:idle`；新增 `bun run perf:smoke`。
- 详细数字与复现步骤写入 [engineering/performance.md](../engineering/performance.md)。

## 全量入库、逐字稿 SSR 与长列表首屏上限

**做了什么**

- **全量 ingest**：本地 5 个 dataset 共 1,897 个 pack 全部投影到 Neon；单进程串行太慢，改为每个 dataset 一个 `bun scripts/ingest-db.ts --dataset <id>` 并行跑。3 个实例中途因瞬时连接错误退出 `partial`，重跑后补齐（`processed 1–2 / skipped N`），最终 `bun run db:verify`：`checked 1897 / problems 0`。
- **对账误报修复**：`verify-db.ts` 原来用 `JSON.stringify` 比较 `dataset_insights.totals`，Postgres `jsonb` 不保留对象键顺序，导致 5 个 dataset 全部误报。新增 `scripts/lib/json-equal.ts`（对象无序、数组有序）并补 5 条测试。
- **逐字稿索引 SSR**：新增 `src/db/queries/transcripts.ts`（`getTranscriptIndex` / `getTranscriptMeta`）；`transcripts.astro` 查库后把 entries 传进岛屿，`TranscriptsView` 不再在浏览器拉远端索引；单场页的「逐字稿」分段可用性也由数据库决定，查询失败时保留客户端索引兜底。`.md` 端点复用同一个查询函数。
- **长列表首屏上限**：`StreamsView` 首屏 100 行、`GalleryView` 首屏 60 张，其余「显示更多」在已水合岛屿内追加；筛选 / 排序变化回到首批，CSV 仍导出完整筛选结果。
- 文档同步：`AGENTS.md`、`docs/README.md`、`architecture.md`、`astro-ssr-migration.md`、`performance.md`、`data-progress.md`、`backlog.md`、`requirements-spec.md`、`data-model.md`、`scripts/README.md`。

**为什么**

- 数据库只有小批量数据时，查询、页面与对账都没有暴露真实规模问题；全量入库才能验收 `dataset_insights`、作者 / 词表 / 付费明细与页面体积。
- 逐字稿索引继续由浏览器从 R2 拉取，与「页面请求期查库」的迁移模型不一致，还多一次首屏网络往返。
- 全组相册 1,897 张封面一次 SSR 到 5 MB HTML；表格 500 行也接近 2.2 MB。首屏没必要全部输出。

**验证**

- `bun run check`：`astro check` 0 error、213 个测试通过、oxlint 0 warning。
- `bun run build`：成功，只预渲染 404 / 500。
- `bun run db:verify`：`checked 1897 / problems 0`。
- 生产构建 + `wrangler dev` + `bun run perf:smoke`（1,897 场）：

  | 路由 | 当前 HTML | 说明 |
  | --- | ---: | --- |
  | `/` | 98.6 KB | 组首页 |
  | `/gallery` | 1.65 MB | 上限前 5.0 MB |
  | `/nonoka/streams` | 1.16 MB | 上限前 2.2 MB |
  | `/nonoka` | 894 KB | 成员首页 |
  | `/nonoka/stream/<id>` | 696 KB | 单场页 |
  | `.../<id>.md` | 14.0 KB | Agent 视图 |
  | `/sitemap.xml` | 192 KB | 1,929 条 URL |

- HTML 抽查：`/gallery` 只输出 60 张封面 + 「显示更多」；`/nonoka/streams` 100 行 + 「再显示」。
- `bun run db:query`：列表 + insights p50 122.5 ms / p95 247.6 ms（本机 → ap-southeast-1）。
