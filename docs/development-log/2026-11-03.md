## Astro + PostgreSQL + Workers 迁移方案

**做了什么**

- 新增 [planning/astro-ssr-migration.md](../planning/astro-ssr-migration.md)：
  - 结论：Astro 7 + Cloudflare Workers + Neon PostgreSQL + R2；数据页请求期 SSR，稳定页预渲染。
  - 数据模型：`datasets` / `streams` / `stream_details` / `paid_events` / `comments` / `authors` / `stream_authors` / `stream_words` / `dataset_insights` / `transcripts` / `ingest_reports`，预留 `chat_events` 分区表。
  - ingest：本地 pack → 事务 upsert → insights → 报告；ingest 用 `postgres` 直连，Worker 读用 `neon-http`。
  - 页面迁移：React Router 解耦、岛屿策略、URL 状态、SEO / sitemap / 404。
  - Agent 视图：`/{datasetId}/stream/{videoId}.md`，返回 `text/markdown`，含概览、部分指标与逐字稿；不做 `Accept` 协商，不启用 Cloudflare Markdown for Agents。
  - 缓存：Astro 7 route caching + Workers Cache；tag purge；ingest 后调内部 purge 端点。
  - 发布：数据更新不触发前端构建；代码部署与数据发布分离。
  - 阶段 0–5、验收清单、风险与待决。

**为什么**

- 旧 SSG 调研的结论是「不推荐 Astro」，前提是整体 SSG；模板的 `output: 'server'` + DB + R2 形态改变了前提。
- 单场页 SSR 后，新场次入库即生效，不再需要每日构建、R2 反代或 `asset hash` 兼容。
- `.md` 路由给 Agent 一个稳定、结构化、包含逐字稿的入口。

**验证**

- 查了 Astro 7 route caching、`@astrojs/cloudflare` 14、Cloudflare Workers Cache / purge、Workers limits、Neon / Drizzle 驱动的官方文档。
- 用当前数据规模估算：1,892 场、约 151 MB pack、691 万条弹幕；全量弹幕暂不入库。
- 未写代码，未做 PoC；迁移验收见方案第 13–14 节。

**未完成 / 待决**

- Workers 是否直接上 Paid。
- Neon 区域与 dev branch 策略。
- 原始 pack 是否只放 R2，还是库内再留 `datapack_archive`。
- 全量弹幕的优先级。
- `Content-Signal` 的具体取值。
- 是否保留 `?full=1` / `?transcript=0` 这类 Agent 参数。

**与方案的偏差**

- **TypeScript 锁 6**：`astro check` 尚不支持 TypeScript 7（报错直接退出），与模板一致使用 `typescript@6`。这是工具链限制，不是降级业务代码。
- **字体用 CSS 导入而非 Astro Fonts API**：现有 `@fontsource-variable/noto-sans(-sc)` 已在依赖里，CSS 导入是离线确定性的；模板的 Fonts API 需要构建期拉取字体，阶段 0 不引入新的构建网络依赖。
- **统一 `@/` 别名**：模板用 `~/`，本项目现有代码与 `tsconfig` 都是 `@/`；移植的壳层文件已改为 `@/`。
- **`scripts/` 与 `src/legacy/` 暂不进入 `astro check`**：旧链路原本只检查 `src`，先保持边界；接入 ingest 后单独补类型检查。
- **`@astrojs/sitemap` 未安装**：方案用自定义 `sitemap.xml` endpoint（阶段 2），不用集成。
