最重要的三条：

## 二、工具评估：claude-seo 能做什么

它的形态是 **Claude Code 插件**：26 个 skill（Markdown 指令）+ 19 个子 agent + 66 个确定性 Python 脚本。真正干活的分两层：

- **确定性层（可独立跑）**：`page_checks.py`（47 项单页检查）、`transport_check.py`（TLS / 安全头 / http→https）、`agentic_check.py`（robots、llms.txt、Markdown 交付、well-known）、`sitemap_discovery.py`、`pagespeed_check.py`（PSI + CrUX）等。输出 JSON，不依赖模型。
- **判断层**：skill 文档本身就是审计 playbook（评分权重、优先级定义、报告结构、E-E-A-T 框架、质量门槛）。在非 Claude Code 环境里，把这套 playbook 当检查清单人工执行即可，结论一致。

### 本次是怎么跑的

官方安装脚本 `install.ps1` 会写 `~/.claude/skills/seo` 并建独立 venv + 下载 Chromium。这里不装插件，只复用了它的脚本层：

```powershell
git clone --depth 1 https://github.com/AgriciDaniel/claude-seo.git
uv venv .venv --python 3.12
uv pip install --python .venv\Scripts\python.exe requests beautifulsoup4 lxml `
  lxml_html_clean urllib3 trafilatura htmldate courlan

.venv\Scripts\python.exe claude-seo\scripts\sitemap_discovery.py https://ymmt.chilfish.top --json --expand --sample 50
.venv\Scripts\python.exe claude-seo\scripts\transport_check.py  https://ymmt.chilfish.top --json
.venv\Scripts\python.exe claude-seo\scripts\agentic_check.py    https://ymmt.chilfish.top --json
.venv\Scripts\python.exe claude-seo\scripts\page_checks.py      --url https://ymmt.chilfish.top/
```

补充了一轮自写抽样巡爬（`sitemap.xml` → 按 URL 类型分桶，每桶随机取 8 条，共 42 条），以及 curl 直测体积、TTFB、压缩比、`.md` 端点响应头。

### 局限

- `pagespeed_check.py` 走 PSI API，无 key 时直接 429，脚本这条路拿不到 Lighthouse 分数。本文第四、五节的实测数据来自手工跑的 Lighthouse 报告。
- `content_quality.py` 依赖 trafilatura 抽正文，对中日文抽取为空（`extracted_text` 长度 0），这条路走不通。
- 没有跑 `seo-local` / `seo-ecommerce`（本站不是本地商家也不是电商），也没有 Google API 凭据跑 `seo-google`（GSC / GA4 / CrUX 字段数据缺失）。
- 工具对 `www` 子域和 http 的判断需要通过外部网络复核，见 L6。

## 三、发现（静态与边缘层）

> 运行时性能问题（字体、LCP、图片、缓存、对比度）集中在第四节。

### High

**H1 `http://` 未重定向到 `https://`**

```
$ curl -sS -o NUL -D - http://ymmt.chilfish.top/
HTTP/1.1 200 OK
CF-Cache-Status: HIT
Server: cloudflare
```

`transport_check.py` 同样报告 `redirects.http_to_https.redirects_to_https = false`、`hops = 0`。两套独立证据一致。

影响：同一内容存在明文可访问副本；无 HSTS 时，首次访问和站外 http 链接都不会被强制升级；搜索引擎可能把 http 视为独立 URL。

修法：Cloudflare 控制台开 **Always Use HTTPS**（Rules → Redirect Rules 或 SSL/TLS → Edge Certificates），或在 Worker 入口加 301。修完 `curl -I http://ymmt.chilfish.top/` 应看到 `301` + `location: https://...`。

**H2 `/gallery` HTML 超过 2 MB**

| 页面 | 未压缩 | gzip | TTFB（缓存命中） |
| --- | --- | --- | --- |
| `/gallery` | 2,067,850 B | 198 KB | 0.37 s |
| `/arale` | 1,461,378 B | 124 KB | 0.26 s |
| `/arale/trends` | 1,384,359 B | 114 KB | 0.24 s |
| `/` | 294,872 B | 33 KB | 0.27 s |

压缩后传输量完全没问题（约 10:1），但 Googlebot 的 2 MB 上限按**解压前**计算，`/gallery` 已经越界。同时 1–2 MB 的 DOM 解析是真实的首屏渲染成本。

修法方向（与 [long-document-rendering-practices.md](./long-document-rendering-practices.md) 的结论一致）：图库首屏只 SSR 首屏可见项，其余交给客户端增量加载或分页；不要整份数据集倒进 HTML。

### Medium

**M1 SSR HTML 体积普遍偏大**

抽样均值（42 条）：

| 页面类型 | 平均 HTML | 最大 |
| --- | --- | --- |
| 成员 `streams` | 1,426 KB | 1,686 KB |
| 成员首页 | 1,020–1,317 KB | 1,317 KB |
| 成员 `trends` | 1,095 KB | 1,351 KB |
| 成员 `gallery` | 965 KB | 1,222 KB |
| 成员 `transcripts` | 944 KB | 1,165 KB |
| 单场页 | 332 KB | 388 KB |
| 首页 | 287 KB | — |

内联 `<script>` 只有 6.5 KB，`<style>` 264 B——**体积全在服务端渲染出的 DOM 标记本身**，不是 hydration 载荷。所以这是"SSR 把整份列表铺满页面"的问题，不是打包问题。

**M2 缺 `Strict-Transport-Security`**

`transport_check.py`：`hsts.present = false`。当前 TLS 1.3、证书 79 天后到期、`nosniff` / `SAMEORIGIN` / `referrer-policy` / `permissions-policy` 都在，只差 HSTS。建议 `max-age=31536000; includeSubDomains`，确认所有子域都走 HTTPS 后再考虑 `preload`。

**M3 图片缺 `width` / `height`**

首页 9/9 张缩略图都没有尺寸属性，成员页与图库页同样。会造成 CLS。缩略图是固定比例（`thumbs/<id>.jpg`），直接写死宽高即可。

**M4 `/calendar` 与 `/about` 没有 `og:image`**

`page_checks.py` 报 `missing-og-image`。`SEO.astro` 里 `image` 是可选 prop（第 32 行 `{image && ...}`），这两个页面没传。分享时退化成 `twitter:card = summary`（小卡）。

**M5 响应头 `Content-Type` 不带 charset**

```
Content-Type: text/html        # 没有 charset=utf-8
```

页面里 `<meta charset="utf-8">` 在最前面，浏览器不会乱码；但 `requests` 这类按头解码的客户端会退回 latin-1（本次自写巡爬就踩了这个坑，中文长度被算成 3 倍）。`.md` 端点是对的（`text/markdown; charset=utf-8`）。建议在 `middleware.ts` 的 `applyHeaders` 里补 charset。

**M6 结构化数据缺实体层**

- 首页只有 `WebSite`，没有 `Organization`。
- 成员页只有 `BreadcrumbList`，**没有 `Person`**。
- 单场页 `VideoObject` 完整（`name` / `description` / `embedUrl` / `thumbnailUrl` / `uploadDate` / `duration` / `inLanguage`），质量不错。

本站核心是"5 个人 + 场次"，成员页缺 `Person` 等于放弃最该拿的实体信号。

### Low

| 编号 | 问题 | 证据 |
| --- | --- | --- |
| L1 | 无 `Content-Security-Policy` | `transport_check.py` `csp.present = false` |
| L2 | 图库首图 lazy-load | `page_checks.py` `first-image-lazy-loaded`；首图常是 LCP 元素 |
| L3 | 单场页标题 61 字 | 42 条样本中 3 条超 60（`mpWrefKdeeE` / `Xz52b5YZazw` / `jsXtGb7YtHo`），会被截断 |
| L4 | 宽 DOM | 首页一个 `<div>` 有 105 个直接子节点；成员页 2,994 个 DOM 节点 |
| L5 | `llms.txt` 格式不合提案 | 20 条 `malformed-link`、5 条 `notes-without-colon`、2 个空 H2 段。仅格式卫生，非排名因素 |
| L6 | `www` 子域 TLS 握手失败（待复核） | 详见下方备注 |

**L6 备注（`www` 子域）**：`https://www.ymmt.chilfish.top/` TLS 握手失败，本地 DNS 把它解析到 `28.0.2.188`（主站是 `28.0.1.197`），证书 SAN 其实覆盖 `*.ymmt.chilfish.top`。这两个地址都在 `28.0.0.0/8`，不像真实 Cloudflare 出口 IP，**大概率是本机 DNS / 代理产物**。需要在别的网络复核，确认 `www` 没有独立记录后再决定要不要删。

### Info

- `robots.txt` 只有一条 `User-agent: *`，没有针对 GPTBot / ClaudeBot / PerplexityBot 的具名组，也没有 `Content-Signal` 行。所有 AI 爬虫一律落到 `*` 组（当前策略是全放行）。`ai-train=no` 这类信号只出现在 `.md` 响应头上，HTML 侧没有。
- WebMCP、`/.well-known/ai-catalog.json`、`api-catalog`、`ucp` 全部 404——对本站都是 `not applicable`，不用管。

### 做得好的部分

- **Sitemap**：1 个 `urlset`，1,837 条，0 无效 loc、0 重复、0 跨域，`lastmod` 100% 覆盖，最新 2026-11-15。
- **可爬性**：42 条抽样全部 200；未知 URL 返回真 404 而不是软 404；`robots.txt` 正确声明 sitemap 且只挡 `/admin/`、`/api/admin/`。
- **Markdown 交付**：`/arale/stream/xBZHYX6-bFw.md` 返回 `200 text/markdown; charset=utf-8`，带 `X-Robots-Tag: noindex`、`Content-Signal: ai-train=no, search=yes, ai-input=yes`、`Link: <...html>; rel="alternate"`、`Cache-Control: public, max-age=3600`。HTML head 里也有对应的 `<link rel="alternate" type="text/markdown">`。这套是站内做得最规范的 SEO 件。
- **每页单一 `h1`、无标题层级跳跃、无重复标题/描述、canonical 全自指**。

TBT 和 CLS 都是满分——主线程不堵、布局不跳，性能分全被 LCP 拖下来。

### LCP 拆解：不是下载慢

| 子项 | 耗时 |
| --- | --- |
| Time to first byte | 119 ms |
| Resource load delay | 41 ms |
| Resource load duration | 191 ms |
| **Element render delay** | **1,995 ms** |

LCP 元素是首页第一张场次缩略图（`section.flex > div.mb-3 > div.@container > img.size-full`，渲染尺寸 753×424）。图片本身 350 ms 就下完了，但**元素直到约 2.35 s 才被画出来**。`lcp-discovery-insight` 三项全绿（`fetchpriority=high` 已加、可发现、未 lazy），所以不是资源发现的问题。

也就是说：**优化下载体积救不了这个 LCP，得找出那 2 秒在等什么。** 主线程总耗时 1.4 s（Style & Layout 450 ms、Script Evaluate 419 ms），在 4× CPU 模拟下约 5.6 s，量级吻合；而 LCP 图片位于 `<astro-island>` 内部，hydration 顺序也是嫌疑之一。这条需要 Performance 面板录一次 trace 才能定论，本文不给结论。

### 载荷构成：字体吃掉 69%

| 类型 | 请求数 | 传输 |
| --- | --- | --- |
| **font** | **51** | **2,392 KB** |
| image | 15 | 599 KB |
| script | 19 | 283 KB |
| stylesheet | 1 | 84 KB |
| document | 1 | 32 KB |
| 合计 | 91 | 3,440 KB |

51 个字体请求里 **48 个是 `noto-sans-sc`**，合计 2,357 KB；按 URL 统计最大单个 74.9 KB（`noto-sans-sc-119`）。

根因在 `src/styles/app.css` 第 2–3 行：

```css
@import "@fontsource-variable/noto-sans-sc";
```

`@fontsource-variable/noto-sans-sc` 带 **101 个 woff2 子集（共 4.29 MB）** 和 101 条 `@font-face`（`index.css` 单文件 101 KB）。首页用到 48 个 unicode-range 子集，就要拉 48 个文件。顺带解释了 84 KB CSS 的来源——`Layout.css` 未压缩 390 KB，其中两个字体包的 `@font-face` 声明就占近一半。

`font-display` 全是 `swap`，所以这不是字体阻塞渲染的问题，是**真金白银的带宽和请求数**。

### 其他实测发现

- **可访问性：19 处 `color-contrast` 不达标**，集中在侧栏 `text-ink-3` 的次级文字（如 `span.shrink-0.text-caption.text-ink-3`）和 `text-body` 的菜单标签（`span.truncate.font-semibold.text-body`）。改动面很小，是调 `ink-3` token 的亮度。
- **缩略图缓存只有 4 小时**：`Cache-Control: max-age=14400`（实测 `.1280.webp`）。这些对象在 R2 里是不可变的派生图，应该是 `max-age=31536000, immutable`。对比：CSS 和字体（`/_astro/*`）已经是 1 年 immutable，只有 `ymmt-s3.chilfish.top` 这条路没对齐。
- **图片选档其实是对的（这条初版写错了）**：报告里 `deviceScaleFactor` 是 **1.75**（`screenEmulation.mobile: true` 但 `formFactor: desktop`，配置本身有点怪）。753 CSS px 显示位 × 1.75 = 1318 物理像素，选 1280w 正确；408 × 1.75 = 714，选 960w 正确；87 × 1.75 = 152，选 480w 也是最小的可用档。`sizes` 在各调用点都写对了，**不要改 `srcset`**。唯一真的选大的是 `brand-mark.webp`（128px 文件显示 44px，浪费 6 KB）和侧栏 87px 头像没有 240w 这一档（每张多花约 30 KB）。
- **`unused-javascript` 的 1,593 KB 基本都是浏览器扩展**：`chrome-extension://cnjifjpddelmedmihgijeibhnjfabmlf`（752 KB）、`...djnlaiohfaaifbibleebjggkghlmcpcj`（559 KB）等。站点自己的部分是 `client.js` 31 KB、`shell-theme.js` 31 KB、`calendar.js` 26 KB、`group-page.js` 25 KB，量级正常。**这条要打折看，下次跑 Lighthouse 用干净的 Chrome profile 或 `--disable-extensions`。**
- **渲染阻塞 330 ms**：单个 `Layout.wTWVdRAW.css`（84 KB 传输 / 390 KB 未压缩）阻塞首屏。移除 CJK 字体后未压缩体积降到 282 KB。
- **未使用 CSS 21 KB、未压缩 JS 22 KB、legacy JS 10 KB**：都是小数，最后再收拾。
- **移动端会更差**：以上是桌面 + 10 Mbps 模拟。同样 2.36 MB 字体在移动端 1.6 Mbps 下要十几秒。**这份报告不能代表移动用户体验**，建议补跑一次 mobile preset。

### 载荷的真正来源：`astro-island` 的 props

`/gallery` 的 1.89 MB HTML 里，只有 60 张卡片是真实标记，**1.71 MB 是 `<astro-island props="...">` 序列化后的整个 1,837 行数组**（3 个 island，props 合计 1,706,833 字符）。内联 `<script>` 只有 6.5 KB。所以体积不是 DOM 铺满，是把全量数据塞进了 HTML 属性——这也是 Googlebot 2 MB 门限的直接原因，而且被截掉的尾巴只是序列化数据，`<title>`/正文都在前面。这条列为 H2 的严重性可以下调，修复方式见第六节。

| --- | --- | --- | --- |
| Document | 1 → 1 | 32.8 → 301.9 KB | 301.4 → 301.3 KB |
| Stylesheet | 1 → 1 | 84.1 → 275.7 KB | **380.7 → 275.3 KB** |
| Script | 19 → 18 | 283.3 → 805.1 KB | 827.1 → 795.8 KB |
| Image | 15 → 15 | 376.1 → 376.7 KB | 370.6 → 370.6 KB |
| **Font** | **51 → 1** | **2,396 → 35.5 KB** | **2,377 → 35.0 KB** |

字体和解压后 CSS 是这次真正的收益：`@font-face` 101 → 8 让 CSS 少了 105 KB，字体少了 2.34 MB。

### 为什么 FCP 反而变慢了

FCP 2.9 → 5.5 s 不是回归，是本地不压缩造成的：1.6 Mbps 下 302 KB 的 document 要 1.5 s（线上压缩后 33 KB 只要 0.16 s），276 KB 的 CSS 要 1.4 s（线上 84 KB 只要 0.4 s）。仅这两项就差约 2.2 s，与 FCP 的差值吻合。

同理，LCP 的 `elementRenderDelay` 8.7 s 里有一大半是本地未压缩的文本资源（document + CSS + JS 合计 1.38 MB）在 1.6 Mbps 下排队。**部署后的真实数字只能线上复测**，本地这份是悲观下界。

### 部署后预计

按线上的压缩比（document 9.2×、CSS 4.5×、script 2.9×）折算：文本资源约 1,372 KB 解压后 → 约 370 KB 传输，加图片 376 KB 与字体 35 KB，**首页传输约 0.78 MB，比修改前的 3.2 MB 少约 76%**。这是估算，不是实测。

## 六、LCP 的根因：`opacity: 0` 把 LCP 绑到了水合上

线上那份移动端报告里，`elementRenderDelay` 是 **17,229 ms**，而 `resourceLoadDuration` 只有 1,832 ms。图片早就下完了，却隔了 17 秒才算 LCP。原因不在网络：

```
$ curl -s https://ymmt.chilfish.top/ | grep -o '<img[^>]*xBZHYX6-bFw[^>]*>'
<img alt="" class="... transition-opacity duration-300 ease-standard opacity-0"
     fetchPriority="high" loading="eager" src=".../xBZHYX6-bFw.jpg" srcSet="...">
```

`StreamCover` 用 `loadedSrc === src` 决定 `opacity-100 / opacity-0`，而 SSR 阶段 `loadedSrc` 恒为 `null`，所以服务端输出的 `<img>` 带着 `opacity-0`。**LCP 规范不承认完全透明的元素**，它要等到 `onLoad`（或 ref 里的 `node.complete`）把 `loadedSrc` 设上、并且 React 水合跑完。而承载它的是 `client:idle` 的岛屿——4× CPU 的移动设备上，主线程有 6.1 s 的活要干，`requestIdleCallback` 迟迟不来。

修复：首帧直接可见，淡入只用于之后换 `src`。

```tsx
const [firstSrc] = useState(src);   // SSR 与客户端首帧一致，无水合差异
const loaded = !showImage || firstSrc === src || loadedSrc === src;
```

### 效果（同口径 mobile preset，本地 preview）

| 指标 | 只修字体 | 再修 LCP 门控 |
| --- | --- | --- |
| LCP | 12.4 s | **6.0 s** |
| `elementRenderDelay` | 8,720 ms | **2,243–2,392 ms** |
| 请求数 | 40 | 40 |

本地再加了 `<link rel="preconnect">` 指向封面域名（`ymmt-s3.chilfish.top`），省掉首图的一次 DNS + TLS。

> 本地 preview 不压缩，LCP 的绝对值仍被放大；**只有 `elementRenderDelay` 和请求数是可信的**。上线后应按线上实测。多次复跑的分数波动很大（性能 45–56），有 3 次因本地 preview 过慢触发 Lighthouse 超时，不要用单次分数下结论。

## 八、复现

脚本与原始 JSON 未入库（体积大且易过期）。claude-seo 部分按第二节命令重跑。

抽样巡爬的临时脚本逻辑：读 `sitemap.xml` → 按 URL 段分桶 → 每桶 `random.seed(42)` 取 8 条 → 并发 6 抓取，比对 title / description / canonical / h1 / JSON-LD / 正文字数 / 字节数。

Lighthouse 报告用 `python` 直接读 JSON：`audits[*].details.items`、`categories[*].auditRefs` 取分数与权重，`lcp-breakdown-insight` 取子项耗时，`network-requests` 按 `transferSize` 排序。

> 注意：解析 `resp.text` 前要显式按 UTF-8 解码，站点的 `Content-Type` 没有 charset（M5，已修），否则中文长度会算错 3 倍。
