# 需求文档（Requirements）

本目录存放需求规格、用户故事与验收标准。**需求文档是项目真相源**：功能范围的权威描述在此，backlog 与阶段计划为派生执行文档。

## 文档索引

| 文档 | 说明 | 何时阅读 |
| --- | --- | --- |
| [requirements-spec.md](./requirements-spec.md) | 需求规格（PRD）：定位、范围、功能需求（FR）、非功能需求、溯源 | 新增功能、架构变更、判断功能边界 |
| [user-stories.md](./user-stories.md) | 用户故事：按 Epic 分组，标注状态与验收标准 | 理解用户需求、设计新特性 |

## 约定

1. 所有需求文档用中文。
2. FR 编号格式：`FR-{模块}-{序号}`，与 `planning/backlog.md` 的任务编号独立。
3. 每条 FR 有唯一 ID、优先级（P0/P1/P2）、状态（✅ 已完成 / 📋 规划中 / ⏸️ 暂缓 / ❌ 已移除）、验收标准、需求来源。
4. 功能需求变更时同步更新 `requirements-spec.md`，并在「变更记录」追加一行。
5. 新增用户故事时追加到 `user-stories.md` 对应 Epic。
6. 迁移中的目标能力（Astro / PostgreSQL / `.md` 路由）状态标 `📋`，不要写成已实现。

### 验收标准（AC）

- **先写 AC 再实现**：AC 描述可观察的行为和期望结果，不描述实现细节。
- 编号格式：`AC-{模块}-{序号}`；有对应自动化测试时，测试名与编号 1:1。
- AC 必须能失败：故意改坏被测行为时，对应检查应变红；当前用手工路径 + 预期结果验收的条目，标注「手工」。
- 源码扫描只能作辅助检查，不能作为 AC 的通过条件。
- AC 变更时同步更新测试与 `requirements-spec.md`，并在开发日志记录原因。
