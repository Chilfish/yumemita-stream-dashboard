# 通用约定

- Expects current/latest major versions of dependencies (e.g. React Router 8, not 7) and will link the official docs to correct a stale version assumption — check the official docs for the current major before picking a version. Confidence: 0.6
- For brand-owned visual artifacts (share/social cards and the like), ground the design in the brand's own official artwork rather than inventing decoration: he explicitly preferred stretching the official brand background image to fit over a custom purple gradient with member-color glows ("背景的紫色再加成员色光晕其实不太好看…用这个官方的背景拓展开来还挺好的"). He also strips decorative chrome that carries no information — no left color border, no redundant "pre-scheduled" badge, no all-members avatar row, no generation timestamp — treating each as noise ("预定的badge是啰嗦不必要的", "border-left 不要"). And alignment/craft is checked pixel-level: a type icon and its label must sit on the same baseline, kept tight to the member name rather than floating on its own row. Confidence: 0.5
- Wants commits made as work progresses ("记得随手commit") — commit at logical checkpoints during the task instead of leaving everything uncommitted at the end; finishing a long task with a clean tree still uncommitted earns a repeat reminder ("额依旧记得随手commit"). When a batch of unrelated changes is pending, expects them split into several segmented/logical commits following the commit convention (type(scope): summary) rather than one catch-all commit ("分段按规范commit所有的更改"). A commit should be packed to the current task's own changes even when parallel work is dirty in the same files — stage only his task's hunks and leave the rest uncommitted — and when he says to commit, that's the whole job: skip verification/pre-commit checks and just make the commit ("你只需要提交你的更改就行，no verify"). Splitting granularity is the *file* level, not the hunk level: grouping whole files into logical commits is enough, and hunk-by-hunk staging is over-engineering ("其实你可以按文件级别来commit就行了"). Because of that, hunk-level git gymnastics are unwanted on safety grounds too — unstaging/reverting and restoring changes just to carve out chunks is to be avoided outright ("不用按chunk来拆分，直接以文件为单位，所以就不用又撤销与还原更改了，免得出问题"): skip verification for the whole run ("全程noverify就行") and stage/commit whole files with plain, non-destructive git commands. Confidence: 0.9
- After finishing a change, expects related docs and the roadmap/next-steps list to be updated, not just the code — and the status/progress docs must be brought in line with reality *before* the commit ("记得先更新文档的状态"). Confidence: 0.6
- "文档即为事实": documentation is held to factual accuracy, not aspiration — routes, file paths, commands and field names in docs must match the current code, stale references (deleted screenshots/assets, old route syntax) must be cleaned up, and plans belong in the roadmap rather than being written as if they already exist. Fixing this counts as in-scope, not a follow-up ("额这倒确实得顺手改了，文档即为事实"). Confidence: 0.6
- Performance work must be written up in the docs, not just shipped in code ("相关的性能优化记得写到文档里记录"): expect a performance record with the before/after sizes and timings, the data-flow/caching reasoning, and the commands to re-check it — measured numbers, not adjectives. Confidence: 0.55
- When a list of identified issues is presented with a recommended subset, doesn't want the rest deferred as "low value for now": the answer is "全都改了吧" — fix every item on the list, including the ones the agent judged not worth the effort, rather than triaging down to the cheap/low-risk fixes. Scope expectations for a perf pass likewise extend to the offline/scripts side (daily-update and ingest scripts), not just the request-time read path. Confidence: 0.5
- Performance is a standing constraint on implementation, not a later optimization pass — he green-lights a plan with a reminder attached ("可以开始按计划实施，…；记得性能问题"). When adding features, keep the existing payload/query budget: reuse data already loaded rather than issuing extra round-trips, and don't let a new panel quietly grow what the page fetches. The motive is also monetary — the database is billed per usage, so avoiding unnecessary requests is a hard requirement, not a nicety ("毕竟这是按量计费的，我不想太多没必要的请求"): when he asks about DB optimization he expects the per-page query/round-trip counts enumerated, redundant or over-fetching queries called out with a priority ordering, and correctness hazards surfaced alongside the cost ones. Confidence: 0.55
- For incremental/batch work (e.g. backfilling data), wants a dedicated index/progress doc that marks where things stand — what is done, what was skipped and why, and what comes next. Confidence: 0.5
- On narrow screens, prefers data-dense charts to scroll horizontally at a minimum plot width rather than being squeezed/compressed to fit ("可以让它横向滚动，就不用太收缩了") — shrinking scale/height to fit mobile width is the wrong tradeoff. Confidence: 0.5
- Judges UI against the "AI slop" tell: oversized corner radii plus heavy drop shadows on every card are a defect ("那些大圆角大阴影的card也是很受诟病的一类", "还是有些AI Slop生成的味道"). Prefers restrained radii and shallow/flat layered surfaces — grouped-background surfaces, hairlines and material-like layering — and asks "Apple 会怎么处理" as the reference for depth instead of floating shadowed cards. Confidence: 0.65
- Design taste leans toward Apple-style visual language: clear focal hierarchy and typography, and explicitly dislikes pages that read as a homogeneous "pile of cards" or stack many equally-weighted dense blocks with no obvious starting point ("首页的信息密度太多了，都不知道从哪里开始看") — is fine with (even wants) a large-scale rethink rather than incremental polish when the overall layout feels off. Confidence: 0.65
- Apple's HIG is the *normative* spec for visual work, not just a vibe reference: he will call it out by name ("颜色方面注意 HIG 规范"). For color this means semantic tokens rather than ad-hoc hexes — system grouped/secondary/tertiary backgrounds for surface layering (hierarchy by luminance, dark mode getting brighter as you go up), label / secondaryLabel / tertiaryLabel for text, separators for hairlines — with accent colors reserved for content and interactive elements and system chrome (scrollbars, framework surfaces) left neutral. Contrast is expected to be verified against those tokens, not eyeballed. Confidence: 0.6
- Finds a flat, plain-gray page background monotonous and cold ("朴素的灰色…总觉得有些单调…免得单调得有些冷了") — wants some warmth/atmosphere in the shell rather than relying only on the member accent color, but explicitly demands restraint ("也需要克制有些"). Confidence: 0.5
- Treats motion/animation as part of the design bar, not decoration: expects transitions and animations throughout the UI (panels/sheets mounting, route and tab changes, chart draw-in, hover states) aligned with Apple-style motion principles, and wants them built on modern browser/CSS capabilities rather than heavyweight JS animation libraries ("最好也能用上现代浏览器的特性"). Confidence: 0.5
- Expects layouts never to overflow horizontally: no page-level horizontal scrollbar at any viewport width (desktop down to ~320px). Wide content (charts, heatmaps, tables) must be contained or scroll inside its own box instead of widening the page — a blown-out width is reported as a bug, not a nitpick. Confidence: 0.6
- A redesign must not trade away information density: retain existing data/tables/metrics and treat the old design as a base to optimize, not replace; achieve calm by layering (quiet shell, dense data) and progressive disclosure across separate pages (member home / stream list / detail) rather than by cutting data. Confidence: 0.65
- On design-direction questions, expects external grounding: identify comparable mature/well-designed products worth referencing (search for them rather than recommending from memory) — and when the subject is a design/AI-coding phenomenon rather than one product, he wants it researched and corroborated with real cited blog posts / community threads ("可以去搜索调研一下相关的博客或者帖子来佐证一下"), not reasoned about from authority — and reason from the end user's first-visit perspective — what that visitor cares about and which data actually serves them — before proposing a direction. Confidence: 0.5
- When generating a large amount of content into a file (big HTML/docs/code blocks), prefers it be written in append chunks rather than one giant write, to avoid size-limit/truncation errors. Confidence: 0.65
- Once options/trade-offs have been laid out, doesn't want to be asked to pick one: expects the agent to just proceed with the implementation it judges best per best practices and its own trade-offs ("你直接开始按最佳实践和取舍来实现就行"), keeping the user for review of the result rather than for approval of each decision. Confidence: 0.55
- Skips design artifacts unless asked: doesn't want design prototypes/mockups or a separate proposal stage — research the codebase and references, decide on an approach, and implement it directly in the real code ("不需要design的原型啥的，你直接调研后想一些方案并实施"). Confidence: 0.6
- Treats prototypes as design validation only, not production code: the real implementation must be built from the project's existing UI library/primitives (e.g. coss ui) — don't introduce a parallel component system or ship the prototype's ad-hoc markup/styles. Within that, hand-rolled markup where a primitive exists is a bug: e.g. search fields must use the library's InputGroup with an end-icon addon, not a raw Input with an absolutely positioned icon ("搜索框是这么用的", with the docs link). Reiterated at the design level: even where the project owns the component library, custom-built components are to be avoided ("得避免手搓组件") — assemble from it rather than hand-rolling surfaces. Confidence: 0.7
- Long text in table cells (e.g. stream titles) must not be truncated: let it wrap/overflow onto multiple lines instead of clipping with `truncate` + a max width ("标题应该不截断，溢出换行就行"). The same "don't hide content behind an affordance" rule applies to list/grid cells holding more items than fit: he sent back a calendar month grid that showed the first two events plus a `+N` counter, expecting every event of that day to be rendered and the cell to grow with its content — an overflow counter or "see more" fold is the wrong answer to constrained space. Confidence: 0.6
- A single flagged UI defect is a symptom, not the scope: when he sends one broken screenshot on mobile ("然后移动端…… 应该不止这一处") he expects the whole surface audited for the same class of problem and every occurrence fixed in the same pass, not just the spot in the image. Confidence: 0.5
- Expects mobile/responsive work to be verified with real device emulation (an actual iPhone device profile — viewport + DPR + touch — not merely a narrowed desktop viewport) and to be screenshotted that way before claiming mobile is fixed; he checks whether that was genuinely done ("你真的有用iPhone手机大小来响应式截图吗"). Confidence: 0.65
- Cares about typography as a core part of UI quality: use a font stack that covers Chinese, Japanese and English consistently, and keep the type scale sensible on both mobile and desktop — mobile is the primary target for design and interaction, so tune layout/sizes for it first. Confidence: 0.6
- Design/UX documents should be written in standard professional designer vocabulary (hierarchy, density, type scale, tokens, progressive disclosure, states) rather than ad-hoc prose. Confidence: 0.55
- For long batch jobs, prefers the agent to hand over a standalone runnable script (added to the repo) that the user runs and monitors themselves, instead of the agent babysitting a background run — and the script should be concurrent, resumable/idempotent (skip already-processed items), and report progress. Confidence: 0.6
- Keeps `package.json` scripts scoped to the project's main line ("这里不用留那么多和项目主线无关的"): one-off data-repair/backfill/maintenance scripts must not be registered as npm scripts — document them (invoked as `bun scripts/<name>.ts`) in the scripts README instead, and main docs should link there rather than listing them. Confidence: 0.7
- In batch/pipeline scripts, expects per-item failures to be skipped and logged, never fatal: known-unrecoverable cases (e.g. future/unstarted streams) should be classified as skips that don't count as failures and don't block the remaining items ("异常处理记得跳过而不阻塞"). The same rule is expected of the input-validation side when a batch is fed a folder: malformed items (e.g. frontmatter missing `videoId`) should be auto-skipped with a reason and the run should carry on ("然后自动跳过那些不合规范的文档，例如 frontmatter 缺少 videoId"), not abort on the first bad file — a batch entry point that dies on the first non-conforming document is a defect. Confidence: 0.7
- Prefers real SPA routing over local-state tab switching: view/page state (and similar navigable context) should live in the URL so pages are deep-linkable and back/forward works, with a sidebar for navigation. Confidence: 0.65
- Keeps raw/source data out of git: derive the committed artifacts locally before commit/push (pre-push compute step) rather than checking in originals, and expects advice to respect that boundary. Confidence: 0.55
- Large/bulk data artifacts should live on object storage (Cloudflare R2 / S3-compatible) rather than in the repo, with the storage base URL kept in an environment variable that is inlined at build time.
- Shared/global resources must be stored once, keyed by their natural scope, not copied per entity: mirroring the same asset into every member's dataset folder is called out as duplication ("你好像整重复了… 为啥不是新建一个 youtube 的文件夹来单独处理呢，表情id的scope 前缀就是不同的") — partition storage by the id's scope prefix (e.g. `emojis/youtube/` vs `emojis/<member>/`) and dedupe/clean up the stale copies. Confidence: 0.6
- Strongly prefers a single source of truth in data pipelines: derived artifacts (manifest, pre-aggregated insights) should be generated from the source data and written to the same destination in the same publish step, rather than kept as a second copy that is manually updated — "单一数据来源是最好的", explicitly to eliminate the "someone forgot to sync / silent drift" failure mode. Confidence: 0.6
- Oversized single-file components are a defect: when a component has grown into one big file, expects it split by the repo's conventions as part of the same task ("并同时按规范拆分后者的组件代码…现在全都堆在了一起") — form state/types and pure helpers pulled into their own modules, presentational pieces (form, list) into separate components, the original file reduced to the container. Splitting is in-scope, not a follow-up to mention.
- Duplicated logic is a defect, not just untidy: shared decisions (a `LOCAL`-style master switch, "is this URL local" checks, config defaults) must live in exactly one module every caller imports — scripts, build config and `src/` alike — instead of the same conditional re-written per file. He interrupts to ask "这个开关的判断会是有个统一的地方吗" and reminds "记得代码复用和维护性，免得到处写同样的逻辑", and he also expects a genuine verdict on whether the design itself is sound, not just compliance. Confidence: 0.7
- Prioritizes a clean git/repo state over preserving history: when tracked files are a mess, is comfortable with rewriting history or deleting and re-committing to make it clean ("让它干净"). Confidence: 0.5
- Expects repeated upload/publish steps to be incremental, not full re-runs ("应该能增量更新上传吧"): keep a local record of what was already pushed and reconcile it against the remote (so unchanged items are skipped and missing/changed remote objects are re-sent), with the local and remote state kept in sync. Extends to the read side of scheduled pipelines too: rather than re-pulling all source data every run, read just the index/manifest to diff for new items and fetch exactly those, then publish only the change ("定点增量地发布数据…只需要拉取索引manifest相关的配置就行，就不必每次都全量拉取全量发布了"). The same instinct applies to derived aggregates: a full recompute of totals/insights every run draws a "所以为啥不是增量地来…要么是找个缓存的地方放着历史数据" — expect the agent to explain/justify the full-recompute cost model and to prefer incremental maintenance of the aggregate or cached intermediate state over re-deriving everything. The diff itself should be grounded in a data-volume comparison against the remote's own state (existing `list()` sizes, DB counts) rather than in local bookkeeping alone, and obtained through interfaces that already exist ("应该是有已有的接口可以获取到的") rather than new tracking; a blind full overwrite is what he is objecting to ("免得总是全量上传覆盖了"). This is the standing *default* for the whole pipeline, not just the upload step: every sync/publish run should process only new items by default — "每次同步或者发布的时候，就默认只处理新增的就行。无论是ingist阶段还是哪里" — so each stage (ingest, verify, publish) filters to the missing/new IDs and leaves existing rows untouched, with rewriting existing data behind an explicit opt-in flag. Confidence: 0.6
- In the recurring daily pipeline, already-known change IDs should be carried forward and handed to the downstream stages ("可以存一下当前获取更新的id，再传下去。这样能避免一些没必要的查询"), not recomputed by re-querying. Any diff/reconciliation pass should be bounded to a recent window — roughly the last week — rather than sweeping all history, on the premise that historical data is immutable and already synced ("感觉最多只要查最近一周的就行，毕竟历史存量的都有了肯定不变"). Treat "how far back does this scan" as an explicit, configurable knob rather than "always everything". Confidence: 0.6
- Data updates must not require a frontend rebuild: anything the page needs to build at deploy time (index/manifest/aggregates) should be computed during the publish step and fetched from object storage at runtime, so publishing data is sufficient and a refresh shows the new data ("现在生产页面上还是旧的数据，这太不同步了太难用了"). Confidence: 0.6
- A publish step must also invalidate the affected cache, not rely on the TTL expiring ("我感觉发布后就是得顺便刷新缓存啊"): after data/transcripts are pushed, the same publish path is expected to purge the relevant cache tags (and the affected dataset/entity tags) so the live site reflects it immediately, instead of leaving it stale until expiry or requiring a manual purge command. Confidence: 0.55
- Architecture default is client-local-first with lazy loading (load/slice data on demand in the browser) rather than server-side compute or a database. Eager loading is reported as a bug: if a page refresh pulls in a pile of content files at once (e.g. `import.meta.glob` with `eager: true`), he expects it reworked so only the item being viewed is fetched ("为啥不是看到时才懒加载?") — building an index/manifest for listings is fine, but bodies load on demand. Confidence: 0.55
- Prefers the agent to perform repo/hosting configuration itself (e.g. set GitHub Actions repository variables via `gh variable set`) instead of handing back a "you need to do this manually" checklist — "你帮忙用 gh cli 来处理就行". Restated as an impatient correction when it was still left as a to-do ("额那你用 gh cli 加进去就行了"): repo-side settings count as part of the task and should be finished via the CLI before reporting back. This covers generating the secret values themselves as well as setting them — tokens/secrets should be created and pushed to Worker/GitHub without him doing it ("token啥的你帮我来生成和更新"). Confidence: 0.7
- After a PR is merged, expects the follow-through to happen without being asked again: sync the local checkout to `main` (pull, clean up the merged branch), then continue with whatever the merge unblocks — reconfigure/redeploy and update the docs — instead of reporting back with a to-do list ("我已经merge了，你帮我本地checkout处理一下，然后继续后续的事项：该配置重部署、改文档等等"). Confidence: 0.5
- Brand/member accent colors must render exactly as authored (e.g. the yellow `#ffcb5b`) — silently darkening them via automatic contrast adjustment is not acceptable ("我希望最终的颜色还是#ffcb5b"). Solve readability by splitting tokens instead: keep the raw color for charts/dots/bars and derive a separate ink token for small text and focus rings. The ink variant should be visibly darker, not merely nudged to the 4.5:1 minimum — a barely-passing darkening still reads as too light ("颜色可以深一些"). The primary/role color should be taken verbatim from the data config; color-tone shifting is only acceptable (if at all) on secondary tones, not on the main accent ("不用整什么色调偏移…最多是用到次色调上，角色的主色调就直接用data里的配置"). Confidence: 0.7

Confidence: 0.7

- Judges data tables by richness and consistency, not just correctness: a table that only renders bare rows/plain numbers reads as "简陋"/incomplete — expects the shared table component used to its full capability (sorting, sticky header/first column, row links, totals/delta comparison rows, inline visual encoding like share bars or sparklines) and consistent treatment across pages.
